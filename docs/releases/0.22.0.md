ManiOS 0.22.0 makes the **`gfx=auto`** linear framebuffer from
[0.21.0](https://github.com/zygvlogs/manios/releases/tag/v0.21.0)
actually usable on a real machine: the kernel console now draws into
it, an explicit resolution can be asked for, and a page-table collision
that black-screened the boot is fixed. ManiOS is an independent
operating system for i386 PCs with its own kernel (ZKT), userland,
desktop (ManiDE), disk operating system (ManiDOS) and drivers.

0.21.0 set a real adapter's VESA mode, but the kernel still wrote its
boot log to the VGA text buffer -- which a VESA mode has replaced, so
the screen went dark the moment the loader handed over. This release
gives the kernel a software text console that draws into the linear
framebuffer, so the whole boot, the shell and every program are visible
on a real card, not only in an emulator.

This is a **pre-release**, tested in QEMU (on three different display
adapters, none of them QEMU's own Bochs-compatible one).

## What's new

- **The kernel console on a linear framebuffer.** When the boot loader
  has set a VESA mode, `zkt/drivers/lfb_console.c` draws the kernel's
  own text -- the boot log, the shell, every program's output -- into
  the framebuffer with an 8x16 font, including the ANSI colours and
  cursor movement the text console already understood. On a machine
  with no Bochs VBE adapter, `gfx=auto` now shows a working ManiOS
  instead of a black screen.
- **`gfx=WxH`** on the boot line: the same VESA probe as `gfx=auto`,
  but asking for the biggest mode that fits within `W` by `H` (e.g.
  `gfx=1400x1050`), so a panel's native resolution can be selected
  explicitly instead of capping at 1024x768.
- **`manide` matches the screen.** Started with no size, ManiDE now
  takes the current framebuffer's size (the fixed VESA mode, or a Bochs
  VBE mode already set) rather than always asking for 800x600.

## Fixed

- **A page-table collision that black-screened the boot.** The kernel's
  own page tables lived in the page-directory entry a 1024x768x32
  framebuffer's window reaches, so mapping the framebuffer overwrote a
  page table with device memory and the kernel faulted on the next
  instruction it fetched through it -- a black screen, with nothing on
  the serial line to say why. The tables now live in the entry just
  below the recursive one, out of every device window's way
  (`zkt/arch/i386/memlayout.h`, `paging.c`, `zkt/mm/mmio.c`).
- **Leaving graphics on an LFB machine no longer faults.** A VESA mode
  can't be undone (no V86 monitor to call the BIOS with), so `fbctl`'s
  `text` command now leaves the framebuffer mapped and the console
  drawing to it, instead of unmapping the memory the console was still
  writing to. The screen stays in graphics, as documented, and the
  machine keeps working.

## Changed

- The boot loader no longer fills the framebuffer red or beeps the PC
  speaker while probing: those were bring-up aids, not behaviour.

## Known limits

The mode is set once, at boot: no changing its size, and no way back
to text mode that is sure to work on every card (M21's own notes,
[docs/milestones/M21-vesa-lfb.md](https://github.com/zygvlogs/manios/blob/v0.22.0/docs/milestones/M21-vesa-lfb.md#known-limits)).
32-bit colour only; with `gfx=auto` at most 1024x768, larger only by
asking with `gfx=WxH`. Otherwise as 0.21.0: no USB, Intel HD Audio,
NVMe or SCSI; ManiOS's FAT drives are read-only to files; no floating
point in programs; no signals. None of ManiOS's drivers, this one
included, has met real hardware other than the one that found this gap
yet: reports are welcome.
